# Локальный harness для Ollama/custom-пресетов: протокол, формат пака и границы ядро/пак

> Status: **implemented** (LocalProtocol / HarnessConfig / OpenAIAgentRun protocol mode /
> ChatPanel wiring / ChatTests cases / packs.json registration). Проверка: ядерные файлы
> проходят syntax-check, минимальный standalone-бинарник из chat-кода проходит все 19
> assertions (протокол + загрузка пака + fallback). В приложении тесты идут через
> `INFINITE_CHATTEST=1` (ChatTests.cpp).
> Прецеденты: `src/core/Extensions.h` (паки), `src/nodes/TrackNodeBase.cpp` (паттерн PackDir),
> `src/core/bci/BciRuntime.cpp` (динамическая загрузка C-ABI библиотеки из пака).

## 1. Цель и ключевая идея

Локальные модели через Ollama (`/v1`) уже технически подключены к `OpenAIAgentRun` —
harness есть. Проблема в том, что harness опирается на **нативный tool-calling**, который
слабые локальные модели выполняют плохо: путают аргументы, нарушают JSON-schema,
«отказываются» звать инструменты.

**Ключевая идея:** даём модели простой **текстовый протокол**. Модель пишет обычный текст
с фиксированными тегами; **детерминированный парсер в ядре** превращает эти теги в
вызовы инструментов, которые выполняются через существующий `propose`-gate. Модель остаётся
«мозгом», но не ручником: все изменения графа идут через gate с откатом, как сейчас.

**Что достигается:**
- Модель не должна корректно эмитировать нативные tool_calls — только писать текст.
- Tuning поведения (промпт, набор инструментов, жёсткость) выносится в **пак**, и
  дорабатывается **без пересборки приложения** — через Settings > Extensions.
- При отсутствии пака система работает на встроенных значениях по умолчанию.

## 2. Граница: что в ядре, что в паке

| Слово | Место | Пример | Зачем там |
|---|---|---|---|
| Транспорт | **ядро** | `Platform::HttpPostStream` → `/v1/chat/completions` | HTTP/SSE, один на все presets |
| Парсер SSE | **ядро** | `OpenAIStreamParser` (уже есть) | общий для всех эндпоинтов |
| **Парсер протокола** | **ядро** | НОВОЕ `LocalProtocol.h/.cpp` | детерминированный, ~120 строк, аппробован в самотестах |
| Выполнение инструментов | **ядро** | `ToolExecutor` → `HandleRpcCommand` → `propose` gate | безопасность, откат, один undo-шаг |
| Цикл шагов / fallback | **ядро** | `OpenAIAgentRun::RunThread` (расширяется) | общий цикл, maxSteps, повторы |
| **Системный промпт** | **пак** | `harness.json` | подогнать под слабую модель без пересборки |
| **Набор инструментов + описания + примеры** | **пак** | `harness.json` | fewer tools = выше точность; данные |
| **Жёсткость протокола** | **пак** | `maxSteps`, `maxParseErrors`, `allowMultiAction` | баланс точности и контроля |
| **Парсер как нативная библиотека** | **пак (НЕ сейчас)** | `lib/libHarnessParser.so` | только если парсер станет большим и будет часто меняться |

**Прямо сейчас в пак — только данные. Код парсера в ядре.** Прецедент с BCI
(`BciRuntime`) показывает, что нативные библиотеки в паке *возможны*, но это heavier
вариант — рассмотрен в §7 как отложенный путь.

## 3. Текстовый протокол (v1)

Модель отвечает обычным текстом, содержащим **теги в начале строки**. Все теги
нормализуются в верхний регистр.

### 3.1 Теги

| Тег | Назначение | Формат |
|---|---|---|
| `TEXT:` | Обычный текст для пользователя. Может быть несколько; склеиваются. | любые строки до следующего тега |
| `PROPOSE:` | Выполнить пакет изменений через propose-gate. **Один тег на ход.** | JSON-объект |
| `CHECK:` | Проверить результат предыдущего propose (звук, NaN, обрезка). | JSON-объект |

### 3.2 Формат JSON

`PROPOSE:` принимает такой объект (аналог нативного инструмента `propose`):

```json
{"label": "add a 60Hz sine", "calls": [{"method": "create_node", "params": {"type": "Analog", "x": 100, "y": 100}}]}
```

`CHECK:` принимает:

```json
{"reset": false}
```

### 3.3 Пример ответа модели

**Ход 1** — объяснение и предложение изменения:

```
TEXT: Добавлю синус и проверю, что он звучит.
PROPOSE: {"label": "sine", "calls": [{"method": "create_node", "params": {"type": "Analog", "x": 100, "y": 100}}, {"method": "set_param", "params": {"index": "@0", "key": "freq", "value": 60}}]}
```

**Ход 2** — после результата PROPOSE, проверка результата (правило §3.4: один действиявальный
блок за ход; если модель кладёт PROPOSE и CHECK в один ответ, выполняется только PROPOSE,
CHECK игнорируется с пометкой):

```
CHECK: {"reset": false}
```

### 3.4 Правила парсинга (детерминированные, для слабых моделей)

1. **Текст до первого тега** (если тегов нет) — ответ как есть, ход завершён.
2. **`TEXT:`** — всё после двоеточия до следующего тега; несколько `TEXT` склеиваются
   в один непрерывный ответ, который показывается в чате.
3. **`PROPOSE:` / `CHECK:`** — JSON начинается после двоеточия. Для гибкости с
   pretty-print'ом: берутся все строки **до строки, начинающейся с другого тега**,
   или до конца ответа. Собираются в один текст, `nlohmann::json::parse`.
   - Если JSON непарсятся → инструмент выдаёт ошибку + сырой текст + инструкцию
     «верните один корректный JSON-объект». Ход продолжается (инкремент `maxParseErrors`).
   - Если JSON парсятся, но не объект (например, массив) → ошибка аналогично.
4. **Один действиевальный блок за ход.** Если в одном ответе два `PROPOSE:` или
   `PROPOSE:` + `CHECK:` одновременно — выполняется **первый**, остальные игнорируются,
   в ToolResult уходит заметка «один инструмент за ход, сделайте еще один ход».
   Это защита слабых моделей от «сделал два editа сразу, не зная результата первого».
   Переключение тумблом `allowMultiAction` (по умолчанию `false`).
5. **Неизвестные теги** (`TRY:`, `TOOL:` и т.п.) — игнорируются, но в ToolResult
   записываются, чтобы пользователь видел, что модель хотела сделать.
6. Если **нет ни одного действиявального блока** — ответ считается «просто чат»,
   ход завершается как успешный (то же, что сегодня в plain-chat fallback).

### 3.5 Ошибки и повторы

- `maxParseErrors` (default 2): после этого количества подряд неудачных парсингов
  движка — `End` с понятным сообщением («модель генерирует некорректные команды,
  переформулируйте запрос проще»). Ход не «висит», пользователь видит причину.
- Ошибка выполнения инструмента (propose отклонил) — результат **отдаётся обратно в
  контекст модели** как сообщение `tool`, как в текущем цикле: модель видит ошибку и
  может исправить в следующем шаге. Это уже функция существующего цикла.
- Ошибка сети/HTTP — как сейчас: `End` с сообщением, без бесконечных попыток.

### 3.6 Почему не «нативные инструменты с упрощением» (вариант B)

- Вариант A (текстовый протокол) **не зависит** от способности модели к нативному
  tool-calling — это работает с любым Ollama-моделем, даже если она не умеет
  `tool_calls` вообще.
- Вариант B остаётся как **режим в паке** (`"mode": "tools"`): если модель хорошо
  эммитит tool_calls (проверить можно позже, §6), пак может поставить `mode: "tools"`
  и включить нативные инструменты без пересборки. Реализация в ядре поддерживает
  оба режима, выбор из пака.

## 4. Формат пака

Пак name: **`ollama-harness`** (id), published через существующий каталог
(`tools/release/packs.json` → release tag `extensions` → `publish_extensions.py`).

### 4.1 Слой 1: `pack.json` (уже существует, не трогаем)

```json
{"id": "ollama-harness", "version": "1.0.0"}
```

### 4.2 Слой 2: `harness.json` (НОВАЯ схема, schema 1)

```json
{
  "schema": 1,
  "mode": "protocol",
  "systemPrompt": "You are an assistant inside Infinite...",
  "promptFile": "prompt.md",
  "tools": {
    "propose":   {"enabled": true, "description": "...", "example": "..."},
    "check":     {"enabled": true},
    "get_graph": {"enabled": true},
    "get_params": {"enabled": true},
    "list_node_types": {"enabled": true},
    "describe":  {"enabled": true},
    "code_errors": {"enabled": true},
    "status":    {"enabled": true},
    "attention": {"enabled": true},
    "selection": {"enabled": true},
    "explain":   {"enabled": false},
    "panel":     {"enabled": false},
    "view2d":    {"enabled": false},
    "settings":  {"enabled": false}
  },
  "limits": {
    "maxSteps": 12,
    "maxParseErrors": 2,
    "allowMultiAction": false
  }
}
```

- `mode`: `"protocol"` (текстовый протокол) | `"tools"` (нативные инструменты).
- `systemPrompt` — системный промпт. Длинную/читаемую версию можно вынести в
  `promptFile: "prompt.md"`; загрузчик отдаёт предпочтение файлу, если он есть,
  иначе использует встроенный текст.
- `tools` — подмножество инструментов + описания + примеры. По умолчанию для локальных
  моделей — **10 инструментов** (propose, check, get_graph, get_params, list_node_types,
  describe, code_errors, status, attention, selection); 4 сложных (explain, panel,
  view2d, settings) отключены: fewer tools = выше точность слабой модели.
- `limits` — параметры цикла. Клампятся (§5.2).

### 4.3 Разбор папки пака

```
<AppSupport>/extensions/ollama-harness/
├── pack.json        — {"id","version"}
├── harness.json     — конфигурация harness (§4.2)
└── prompt.md        — (необязательно) системный промпт в читаемой форме
```

Установка/отключение/обновление — как у любого пака (Settings > Extensions):
`PackDir("ollama-harness")` даёт путь, `IsEnabled` — включён ли. Отключённый пак
не читается, и harness работает на встроенных default.

### 4.4 Публикация

- `tools/release/packs.json` — добавить `"ollama-harness": {"name": "Ollama Harness", "purpose": "..."}`.
- `tools/release/publish_extensions.py` — без изменений (читает packs.json + release-ассеты).
- Пак更新 без пересборки приложения: новый  zip → новый release-asset → в UI
  появляется «Update».

## 5. Одноразовые изменения в ядре

Все изменения — чистая добавка, без переделки существующего потока.

### 5.1 Новый парсер протокола: `src/core/chat/LocalProtocol.h/.cpp`

- структура `ProtocolBlock { kind; text; json; raw; }`
- `ParseProtocol(const std::string& reply, ProtocolBlock& outText, ProtocolBlock& outAction, std::string& err)`
- плюс хелперы `FindAction(reply, outAction)`, `ParseActionJson(...)`.
- ~120 строк. **Плюсы:** нужен в любом случае; чистая функция, тестируется в
  `ChatTests.cpp` без GUI; не несёт ABI-риска. **Минусы:** второй код-пат параллельно с
  нативным tool-calling — смягчается тем, что выполнение (execution) одно и то же
  (через `ToolExecutor`), отличается только «как достаются вызовы из ответа».

### 5.2 Загрузчик конфигурации: `src/core/chat/HarnessConfig.h/.cpp`

- `struct HarnessConfig { mode; systemPrompt; enabledTools; maxSteps; maxParseErrors; allowMultiAction; sourcePackId; }`
- `HarnessConfig LoadHarnessConfig(const std::string& packId)` — читает
  `<PackDir(packId)>/harness.json` (если пак отсутствует/отключён/сломан — возвращает
  **встроенные default**, источник = "builtin").
- Проверка: `schema == 1` (иначе default + предупреждение); `mode` ∈ {protocol, tools};
  имена инструментов — существующие (ненайденные отбрасываются с предупреждением);
  `maxSteps` 1..32, `maxParseErrors` 0..5 клампятся; длина `systemPrompt` ≤ 8 КБ
  (защита от сломанного/компрометированного пака).
- ~80 строк. **Плюсы:** tuning без пересборки (главная цель); согласуется с паттерном
  паков; жёсткая валидация. **Минусы:** новая схема JSON, которую нужно держать в
  уме; риск, что пак сломает harness — смягчается default-на-fallback + валидацией.

### 5.3 Подключение в `OpenAIAgentRun`

- `Options` получает `HarnessConfig config` (и/или `mode`).
- В `RunThread`: в режиме `protocol` — запрос **без `tools`**, системный промпт из
  конфига, после завершения ответа парсим протокол (§3): `TEXT` → Text-event,
  `PROPOSE`/`CHECK` → `ExecuteToolOnMain` (тот же путь, тот же gate), результат
  → сообщение `tool` → цикл.
- Режим `tools` — как сегодня (нативные инструменты), но с подмножеством из конфига.
- ~40 строк. **Плюсы:** минимум касаний, всё используется; **минусы:** branch в цикле —
  смягчается тем, что ветка узкая и shared-execution.

### 5.4 SATests: `src/app/selftest/ChatTests.cpp`

- unittests `ParseProtocol`: пример из §3.3, pretty-print JSON, два PROPOSE (один выбирается),
  неизвестные теги, сломанный JSON, отсутствующие теги, пустой ответ.
- ~100 строк, без GUI, без network.

### 5.5 Что в ядре **НЕ** делаем (и зачем)

- **Не трогаем** `OpenAIAgentTools()`, `propose`-gate, `HandleRpcCommand` — безопасность
  и откат остаются как есть. Протокол не ослабляет их.
- **Не делаем** нативный parser-lib в паке (§7): сейчас парсер мал и стабильн,
  data-pack — нужное решение.
- **Не меняем** UI SettingsWindow: пак появится в вкладке Extensions автоматически;
  достаточно (можно позже добавить подсказку в панели custom-agent: «harness-пак установлен»).

### 5.6 Сводка за/против по решению

| Решение | За | Против / риск |
|---|---|---|
| Парсер в ядре (вместо в пак) | просто, testable, без ABI-риска | два пути получения вызовов (нативный + протокол) |
| Конфигурация в пак | tuning без пересборки, цель задачи | новая JSON-схема, риск сломанного пака |
| Встроенные default при отсутствии пака | features работают без пака | нужно держать default в sync со схемой |
| `harness.json` отдельно от `pack.json` | не ломает существующую схему паков | два файла вместо одного (минимальна) |
| Нативная библиотека-парсер в пак (BCI-style) | апгрейд парсера без пересборки | ABI/версионирование, dlopen-поверхность, 3-платформенные сборки, загрузка произвольного кода — **отложено** |
| `mode: "tools"` в пак | сильные модели могут нативные инструменты | другой код-пат; нужен только когда проверка покажет, что модель умеет tool-calling |

## 6. Fallback и проверка capability

- **Пак отсутствует/отключён/невалидный** → встроенные default: протокол, default-набор
  инструментов, maxSteps=12. Feature работает.
- **`TestOpenAIConnection`** (CliSetupSection) — по-прежнему проверяет базовое
  соединение. Дополнительно (опционально, ~30 строк, тумбло в паке `"probeProtocol": true`):
  после «Connected» шлёт пробу «Ответьте ТОЛЬКО: `TEXT: PONG`» и проверяет, что ответ
  содержит тег протокола — показывает «protocol-ready». **Риск:** слабые модели могут
  не пройти пробу → ложный negative; поэтому опционально и по умолчанию off.

## 7. Отложенный путь: нативная библиотека-парсер в пак (BCI-style)

`BciRuntime` уже демонстрирует, что паки могут содержать C-ABI shared library
(`<pack>/lib/libBoardController.so|.dylib|.dll`), загружаемую через
`dlopen`/`LoadLibraryExW`, с function-pointer контрактом и graceful fallback.

Аналогично можно сделать `libHarnessParser` — но **не сейчас**:
- **За:** апгрейды парсера без пересборки; нужен только если парсер разрастётся
  и будет часто меняться.
- **Против:** ABI-версионирование (что если signatures изменятся), поверхность ошибок
  dlopen, сборка для 3 платформ в ревью-пайплайне, загрузка произвольного кода в
  приложение (паки уже имеют sha256, но это всё равно heavier).
- **Решение:** парсер в ядре, data-pack. Пересмотреть, если empirics покажут,
  что протокол быстро эволюционирует.

## 9. Что можно настраивать БЕЗ пересборки (итог для задачи)

- Системный промпт (и его читаемая версия `prompt.md`)
- Включенный набор инструментов и их описания/примеры
- Режим: `protocol` или `tools`
- Жёсткость: `maxSteps`, `maxParseErrors`, `allowMultiAction`
- Проверка capability (`probeProtocol`)

Всё это — данные в паке, публикуемые через `publish_extensions.py`. Ядро бранят
только один раз, и дальше tuning идёт как обновление пака.
